# Mavericks Execution Platform - Project Guide

## 1. Project Overview

Mavericks Execution Platform is a React + Vite training management application. It currently focuses on managing training batches, maintaining participant rosters, processing attendance files from Microsoft Teams and Webex, calculating attendance risk, generating a simple attendance summary, and exporting attendance reports to Excel.

The core purpose of the application is to support training execution operations. It gives different user roles a dashboard-oriented workspace and provides batch-level tools for tracking training sessions and participant attendance.

Key features implemented so far:

- Role selector for Admin, Coordinator, Trainer, and Participant workspaces.
- Role-based dashboard screens with mock metrics, focus items, activity, and pipeline progress.
- Batch registry with create and edit support.
- Batch detail page with batch summary, trainer details, lifecycle timeline, meeting link, and participant management.
- Participant entry for internal and external batches.
- Local browser persistence through `localStorage`.
- Teams CSV attendance upload for internal batches.
- Webex CSV attendance upload for external batches.
- Minimum attendance duration filtering.
- Attendance matching against the batch participant roster.
- Attendance percentage, absence, and risk calculation.
- Simple generated batch summary based on risk and unmatched records.
- Excel export with attendance, summary, and unmatched-record sheets.

## 2. Folder Structure Explanation

### Root Files

- `package.json`: Defines project scripts and dependencies. Main scripts are `npm run dev`, `npm run build`, `npm run lint`, and `npm run preview`.
- `package-lock.json`: Locks dependency versions installed by npm.
- `index.html`: Vite HTML entry point. It provides the root DOM node used by React.
- `vite.config.js`: Vite configuration using the React plugin.
- `tailwind.config.js`: Tailwind CSS content scanning configuration.
- `postcss.config.js`: PostCSS configuration for Tailwind and autoprefixing.
- `eslint.config.js`: ESLint configuration for JavaScript, JSX, React Hooks, and Vite refresh rules.
- `README.md`: Default Vite starter documentation.
- `.gitignore`: Git ignore rules.
- `dist/`: Build output generated by Vite.
- `node_modules/`: Installed npm dependencies.
- `public/`: Static assets served directly by Vite.

### `public/`

- `favicon.svg`: Browser tab icon.
- `icons.svg`: Static icon asset.

### `src/`

Main source folder for the application.

- `main.jsx`: React entry point. It mounts `<App />` into the DOM.
- `App.jsx`: Main application shell. It handles role routing, dashboard rendering, batch state, local storage persistence, and navigation.
- `index.css`: Global CSS and Tailwind directives.
- `spec.md`: Short feature list and intended module direction.
- `projectmap.md`: High-level project map and intended flow.

### `src/components/`

Reusable and page-level React components.

- `BatchManagement.jsx`: Batch list, batch creation/editing, batch detail view, participant management, batch timeline, trainer details, and summary panels.

### `src/components/uploads/`

Upload-related UI components.

- `TeamsAttendanceUpload.jsx`: Attendance upload panel. Despite the name, it supports both Teams and Webex based on the batch training type.

### `src/utils/`

Shared logic modules. This is where non-UI behavior lives.

- `teamsParser.js`: Parses Teams attendance CSV rows into normalized participant attendance records.
- `webexParser.js`: Parses Webex attendance CSV rows, filters breakout rows, aggregates duplicate attendee rows, and extracts meeting metadata.
- `attendanceEngine.js`: Coordinates CSV parsing, attendance processing, roster matching, risk calculation, unmatched record detection, and summary generation.
- `attendanceExport.js`: Creates downloadable Excel attendance reports using ExcelJS.
- `storage.js`: Small wrapper around `window.localStorage` for loading and saving JSON data.

### `src/data/`

Mock and static data used by the application.

- `mockData.js`: Defines lifecycle statuses, training types, timeline steps, and initial mock batch records.

### `src/assets/`

Bundled image assets.

- `hero.png`: Image asset currently available in the source tree.
- `vite.svg`: Default Vite asset.

## 3. Module Breakdown

### Role-Based Dashboards

Implemented in `src/App.jsx`.

The application starts with a role selector. The available roles are Admin, Coordinator, Trainer, and Participant. Each role has its own metadata, dashboard copy, metrics, focus items, pipeline values, and recent activity. Routing is handled manually using `window.history.pushState` and `window.location.pathname`, not React Router.

Supported role routes include:

- `/admin`
- `/coordinator`
- `/trainer`
- `/participant`

Each role can access shared navigation sections such as Dashboard, Batches, Candidates, and Reports. Currently, Batches and Candidates route into the same batch management experience. Reports does not yet have a separate implemented page and falls back to the dashboard page.

### Batch Management

Implemented in `src/components/BatchManagement.jsx`.

Batch management includes:

- Batch list table.
- Status summary cards for Planned, Running, Completed, and Closed batches.
- Batch creation form.
- Batch edit form.
- Batch detail page.
- Batch timeline display.
- Trainer details.
- Meeting link access.

Batches are stored in React state in `App.jsx` and persisted to `localStorage` under the key `mavericks_phase2_batches`.

The batch object includes:

- `batchId`
- `trainingName`
- `trainingType`
- `startDate`
- `endDate`
- `timings`
- `status`
- `trainer`
- `coordinatorSpoc`
- `meetingLink`
- `participants`
- `timeline`

### Participant Management

Implemented inside `BatchManagement.jsx`.

Participant fields depend on training type:

- Internal batches use `empId`, `empName`, and `officialEmail`.
- External batches use `name`, `email`, and `mobileNumber`.

Participants can be added and removed from a batch. Participant changes are held in the top-level `batches` state and saved to local storage.

### Teams Attendance Processing

UI entry point: `src/components/uploads/TeamsAttendanceUpload.jsx`

Logic files:

- `src/utils/attendanceEngine.js`
- `src/utils/teamsParser.js`

Internal batches use Teams attendance processing. The upload component accepts one or more CSV files. The Teams processor:

- Parses each CSV with PapaParse.
- Reads the training name and session date from the filename when it matches the expected Teams attendance filename pattern.
- Normalizes participant fields from multiple possible Teams column names.
- Converts duration values into minutes.
- Filters out participants below the selected minimum stay duration.
- Sorts sessions by date.

### Webex Attendance Processing

UI entry point: `src/components/uploads/TeamsAttendanceUpload.jsx`

Logic files:

- `src/utils/attendanceEngine.js`
- `src/utils/webexParser.js`

External batches use Webex attendance processing. The upload component switches to Webex automatically when the batch training type is `External`. The Webex processor:

- Parses each CSV with PapaParse.
- Extracts meeting name and date from Webex metadata rows.
- Ignores breakout session rows.
- Reads attendee display name, attendee email, and attendance duration.
- Converts Webex duration text into minutes.
- Groups repeated attendee rows by name and email.
- Filters attendees below the selected minimum stay duration.
- Sorts sessions by date.

Note: `TeamsAttendanceUpload.jsx` also checks for a `Segue` training type when selecting Webex, but `mockData.js` currently exposes only `Internal` and `External` training types.

### Attendance Engine Logic

Implemented in `src/utils/attendanceEngine.js`.

The attendance engine is the central processing layer. It:

- Parses Teams and Webex files.
- Builds normalized session-level attendance data.
- Converts roster participants into a common identity shape.
- Matches roster participants to attendance records by employee ID, email, or name.
- Produces date-wise attendance marks (`P` or `A`).
- Calculates total duration, session count, present count, attendance percentage, and consecutive absences.
- Detects attendees from uploaded files that do not exist in the batch roster.
- Builds summary counts.
- Generates a simple text summary.

### Risk Engine Logic

Implemented inside `attendanceEngine.js`.

Risk is calculated from attendance percentage and consecutive absences:

- `HIGH`: Attendance below 50%, or 3 or more consecutive absences.
- `MEDIUM`: Attendance below 75%, or exactly 2 consecutive absences.
- `LOW`: Healthy attendance or no uploaded attendance yet.

The engine also creates:

- `riskReason`: Human-readable explanation for the risk level.
- `recommendedAction`: Action text such as escalation, reminder, or no action needed.

### AI Summary Logic

Implemented as `generateBatchSummary(summary)` in `attendanceEngine.js`.

This is currently a rule-based summary, not an external AI API integration. It looks at:

- Number of high-risk participants.
- Number of medium-risk participants.
- Number of unmatched records.

If there are no risk or matching issues, it returns a healthy-attendance message.

### Excel Export

Implemented in `src/utils/attendanceExport.js`.

The export module uses ExcelJS to create a workbook in the browser. It creates:

- Attendance sheet with participant rows, date-wise attendance, duration, counts, percentage, risk, reason, and recommended action.
- `AI Summary` sheet with batch metrics and generated summary text.
- `Unmatched Records` sheet with uploaded attendance records that did not match the roster.

The report applies:

- Header styling.
- Frozen top row.
- Auto-filter.
- Present/absent cell colors.
- Risk-level colors.
- Borders and wrapping.

The downloaded file name currently follows the pattern:

`<batchId>-teams-attendance.xlsx`

This file name is used even when the attendance source is Webex.

## 4. Data Flow

### Step 1: Batch Creation

1. A user enters a role workspace.
2. The user opens the Batches section.
3. `BatchListPage` displays existing batches from React state.
4. The user clicks Create batch.
5. `createEmptyBatch()` prepares a default batch object.
6. The user fills the batch form and submits it.
7. `formToBatch()` converts form state into a batch object.
8. `App.jsx` receives the new batch through `onCreateBatch`.
9. The batch is added to the `batches` state.
10. The updated `batches` state is saved to `localStorage`.

### Step 2: Participant Addition

1. The user opens a batch detail page.
2. `BatchDetailPage` renders the participant form.
3. The form fields depend on `batch.trainingType`.
4. Internal participants are added with employee ID, name, and official email.
5. External participants are added with name, email, and mobile number.
6. On submit, `onAddParticipant` updates the matching batch.
7. The updated batch list is saved to `localStorage`.

### Step 3: Attendance Upload

1. The attendance upload panel renders on the batch detail page.
2. `getAttendanceSource(batch)` selects the source:
   - Internal: Teams
   - External: Webex
3. The user selects a minimum stay threshold.
4. The user uploads one or more CSV files.
5. `handleFiles()` selects the correct processor:
   - `processTeamsAttendanceFiles`
   - `processWebexAttendanceFiles`
6. Processed attendance data is stored in component state.
7. The processed attendance data is saved to `localStorage` using a batch-specific attendance key.

### Step 4: Parsing

Teams parsing:

1. PapaParse reads CSV rows.
2. `parseTeamsFilename()` extracts training name and date from the file name when possible.
3. `parseTeamsAttendanceRows()` normalizes Teams row data.
4. `parseDurationToMinutes()` converts duration values into minutes.
5. `filterParticipantsByDuration()` removes records below the selected minimum stay.

Webex parsing:

1. PapaParse reads CSV rows.
2. `getWebexMeetingMetadata()` extracts training name and date.
3. `parseWebexAttendanceRows()` removes breakout sessions and normalizes attendee data.
4. `parseWebexDuration()` converts Webex duration text into minutes.
5. Duplicate attendee entries are grouped and their durations are summed.
6. `filterParticipantsByDuration()` removes records below the selected minimum stay.

### Step 5: Matching

1. `prepareAttendanceReport()` receives the batch participant roster and processed session data.
2. Each roster participant is normalized through `getRosterIdentity()`.
3. Each uploaded attendee is normalized through `getAttendeeIdentity()`.
4. `getAttendanceMatch()` checks for a match by:
   - Employee ID
   - Email
   - Name
5. For each date, the participant is marked:
   - `P` when matched.
   - `A` when not matched.
6. Uploaded attendees that do not match any roster participant are listed as unmatched records.

### Step 6: Risk Calculation

1. The engine counts total sessions.
2. It counts sessions where the participant was present.
3. It calculates attendance percentage.
4. It calculates the maximum run of consecutive absences.
5. `getRiskLevel()` assigns `HIGH`, `MEDIUM`, or `LOW`.
6. `getRiskReason()` explains why the risk was assigned.
7. `getRecommendedAction()` adds a suggested next action.

### Step 7: Summary Generation

1. `prepareAttendanceReport()` builds summary counts:
   - Total participants.
   - Attended at least once.
   - Never attended.
   - High risk.
   - Medium risk.
   - Low risk.
   - Unmatched records.
2. `generateBatchSummary()` converts the counts into a simple text summary.
3. The upload component displays the summary in the attendance panel.

### Step 8: Export

1. The user clicks Export Excel.
2. `TeamsAttendanceUpload.jsx` calls `exportAttendanceToExcel()`.
3. The export module creates an Excel workbook with attendance, summary, and unmatched-record sheets.
4. The workbook is written to a browser buffer.
5. A Blob URL is generated.
6. A temporary download link is clicked programmatically.
7. The user receives an `.xlsx` file.

## 5. Key Utility Functions

### `teamsParser.js`

Important functions:

- `parseDurationToMinutes(duration)`: Converts numeric, clock-style, or text duration values into minutes.
- `parseTeamsAttendanceRows(dataArray, trainingName)`: Converts raw Teams CSV rows into normalized attendee records.
- `filterParticipantsByDuration(participants, minDuration)`: Keeps only attendees whose duration meets the configured minimum stay.

This file is responsible for handling variation in Teams CSV column names. It supports fields such as full name, email, UPN, employee ID, duration, join time, leave time, and role.

### `webexParser.js`

Important functions:

- `parseWebexDuration(durationText)`: Converts Webex duration strings into minutes.
- `parseWebexAttendanceRows(rows)`: Converts raw Webex CSV rows into normalized attendees, ignores breakout rows, and aggregates duplicate attendee entries.
- `getWebexMeetingMetadata(rows, fileName)`: Extracts training name and session date from Webex data.

This file is responsible for Webex-specific formatting and session cleanup.

### `attendanceEngine.js`

Important functions:

- `processTeamsAttendanceFiles(files, minDuration)`: Parses one or more Teams attendance CSV files.
- `processWebexAttendanceFiles(files, minDuration)`: Parses one or more Webex attendance CSV files.
- `prepareAttendanceReport(batchParticipants, trainingDetails, trainingType)`: Builds the complete attendance report used by the UI and export.
- `generateBatchSummary(summary)`: Creates a simple text summary from attendance risk and unmatched-record counts.

This file is the main business-logic layer for attendance, matching, risk, and reporting.

### `attendanceExport.js`

Important functions:

- `exportAttendanceToExcel({ batch, dates, rows, summary, aiSummary, unmatchedRecords })`: Creates and downloads the Excel workbook.

Internal helper functions style workbook headers, borders, attendance cells, risk cells, summary sheet, and unmatched-record sheet.

## 6. Where to Modify What

### Change UI

- Main role dashboards and navigation: `src/App.jsx`
- Batch list, batch forms, batch details, participant table: `src/components/BatchManagement.jsx`
- Attendance upload UI and report table: `src/components/uploads/TeamsAttendanceUpload.jsx`
- Global styles: `src/index.css`
- Tailwind scanning or theme extension: `tailwind.config.js`

### Change Data or Mock Defaults

- Mock batches: `src/data/mockData.js`
- Lifecycle statuses: `src/data/mockData.js`
- Training types: `src/data/mockData.js`
- Timeline steps: `src/data/mockData.js`

### Change Attendance Logic

- Teams parsing rules: `src/utils/teamsParser.js`
- Webex parsing rules: `src/utils/webexParser.js`
- Matching, risk, summary, and report construction: `src/utils/attendanceEngine.js`
- Excel report layout and styling: `src/utils/attendanceExport.js`

### Change Persistence

- Local storage helpers: `src/utils/storage.js`
- Batch storage key: `BATCH_STORAGE_KEY` in `src/App.jsx`
- Attendance storage key pattern: `getStorageKey()` in `src/components/uploads/TeamsAttendanceUpload.jsx`

### Add New Features

- Add a new page or route section in `src/App.jsx`.
- Add new batch-level UI in `src/components/BatchManagement.jsx`.
- Add new attendance source parsing in `src/utils/` and connect it through `attendanceEngine.js`.
- Add new export fields in `attendanceExport.js`.
- Add new mock data structures in `src/data/mockData.js`.

## 7. Current Limitations

- No backend API is implemented.
- No database is implemented.
- Data is stored only in browser `localStorage`.
- Authentication and authorization are not implemented.
- Role selection is UI-only and does not enforce permissions.
- Routing is custom and minimal; React Router is not used.
- Assessment module is listed in the project direction but not functionally implemented.
- Feedback module is listed in the project direction but not functionally implemented.
- Reports page is not a separate implemented module yet.
- AI summary is rule-based and does not call an AI API.
- Attendance matching is exact after normalization; fuzzy matching is not implemented.
- Uploaded attendance is stored per batch and source in local storage, not in a server.
- Excel export file naming still says `teams-attendance` even for Webex exports.
- Training type options currently include only `Internal` and `External`.
- There are no automated tests yet.

## 8. Future Enhancements

Recommended next enhancements:

- Assessment module for quizzes, scores, pass/fail logic, and topper identification.
- Feedback module for participant feedback forms, trainer ratings, and qualitative comments.
- Supabase integration for persistent database storage, authentication, and row-level access rules.
- Azure deployment for hosted frontend delivery and future API services.
- AI API integration for richer summaries, trend detection, risk explanations, and recommended interventions.
- Dedicated reports page with filters, charts, and downloadable summaries.
- Better route management with React Router.
- Import/export support for participant rosters.
- Fuzzy matching and manual reconciliation for unmatched attendance records.
- Test coverage for parsers, attendance matching, risk rules, and export generation.
- Separate attendance component names for Teams and Webex, or a generic `AttendanceUpload` component.

## 10. Developer Notes

- Keep UI components focused on rendering and user interaction.
- Keep parsing, matching, risk, export, and business rules in `src/utils/`.
- Use mock data while backend integration is not available.
- Be careful when changing participant identity fields because attendance matching depends on employee ID, email, and name.
- Be careful when changing attendance date formats because report columns, sorting, and export output depend on normalized date strings.
- When adding a new attendance provider, follow the current pattern: parse provider rows into normalized attendees, filter by duration, then pass sessions into `prepareAttendanceReport()`.
